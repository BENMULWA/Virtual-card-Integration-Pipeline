1. Overview

MHS Virtual Cards lets your platform issue virtual Mastercards (USD) to your own customers through the Mamlaka Partner API. Mamlaka handles KYC submission, card issuance and card operations; you keep the customer relationship, the app experience and the customer records.

This guide is for the engineers who build and run the integration, and for the operations staff who support customers through onboarding. It covers credentials, pricing, the rules every request must follow, the full customer journey from sign-up to an active card, webhooks, and good operating practice.

Authenticating requests

Send the API key in the X-API-Key header on every request:

curl {{BASE_URL}}/balance \
  -H "X-API-Key: $MAMLAKA_API_KEY"
  • Call the API from your backend only. The key must never be shipped in a mobile app or in browser code.
  • A wrong or missing key returns 401.
  • The rate limit is 600 requests per minute; above it you receive 429.
Key compromised? If the API key is lost or leaked, ask Mamlaka to regenerate it. The old key stops working immediately, so deploy the new key to all backend services straight away.

Getting an exact quote

GET/quote?kind=issue|deposit&amount=10&cardTypeId=111078
{"kind": "issue", "usd": "10.00", "kes": "{{QUOTE_ISSUE_10}}", "cardFeeUsd": "2"}

kind=issue includes the card fee; kind=deposit is the load only.

Funding the float

  1. Pay Mamlaka in KES by bank transfer or M-Pesa.
  2. Send Mamlaka the payment reference.
  3. Mamlaka credits your float once the payment has arrived; each reference can be credited only once.
GET/balance

available is what you can spend. held is reserved for operations still in progress: it is charged if the operation succeeds and returned to available if it fails. If the float cannot cover an operation, you receive 402 and nothing is sent to the card processor.

4. Rules for every call

Idempotency

Requests that create or move something carry an Idempotency-Key header of 8 to 64 characters. Sending the same request again with the same key never repeats the action, which makes retries after a timeout safe.

  • Required on: KYC submit and resubmit, card issuance, deposit, freeze and unfreeze. You may send one on any other request; it is ignored there. (Customer creation is already safe to repeat: it is idempotent on externalId.)
  • Generate one key per business action (for example, one per card issuance or one per deposit).
  • When retrying, reuse the same key. A new key means a new action, which could issue a second card or move money twice.
  • Store the key alongside the action in your database before sending the request.

Identifiers and amounts

  • Customers are identified by your own customer id, sent as externalId and used in URL paths. You never handle Mamlaka's internal customer ids.
  • Card amounts are USD strings with at most two decimals, for example "10" or "10.50". Your float is in KES.
  • Every operation returns a merchantOrderNo: your reference for that operation. Store it.

Operation outcomes

statusMeaningWhat to do
SUCCESSDoneSettle with your customer
PENDINGAccepted, being processedWait for operation.updated, or poll GET /operations/{reference}?refresh=true
UNKNOWN (HTTP 202)The outcome could not be confirmed yetHold your customer's money. Retry with the same key, or poll the operation
FAILEDRefused; your float is not chargedRefund your customer
Never assume failure. On a timeout, a network error or any 5xx, the operation may still have happened. Do not refund your customer and do not retry with a new key: retry with the same key, or read GET /operations/{reference}?refresh=true. Refund only on a definitive refusal (4xx) or a final FAILED.

Most common rejection A wrong date of issue or a missing middle name. Names, ID number and date of issue must match the ID exactly. Show the customer their ID photo next to these fields so they can check before submitting.
Unique email An email already registered for a cardholder is rejected with "Email already exists". The card processor sends the customer a verification code at this email, so it must be an address the customer can actually open.
Customers outside Kenya The card processor decides which countries and ID documents it accepts. Confirm the countries you serve with Mamlaka before onboarding customers there.
5

Wait for the decision

A decision usually takes a few hours. You receive a kyc.status_changed webhook, or can poll:

GET/customers/{externalId}/kyc?refresh=true
StatusMeaningShow in your app
wait_audit / under_reviewWaiting for review"We're verifying your details"
pass_auditApprovedOffer card creation
rejectRejected; see reasonExplain what to fix and let the customer resubmit
Once per person KYC is done once per customer. An approved customer can hold more than one card without repeating KYC.
6

If rejected, fix and resubmit

PUT/customers/{externalId}/kyc/{holderId}

Send the corrected details, with a new Idempotency-Key. Only a rejected application can be updated; do not resubmit one that is still waiting.

7

Issue the card

First get the exact cost: GET /quote?kind=issue&amount=10&cardTypeId=111078. Then:

POST/customers/{externalId}/cards
FieldDescription
cardTypeId111078 for the Mastercard Virtual (USD) card
holderIdFrom the KYC response
amountOpening load in USD, as a string (e.g. "10"). Minimum 10 USD; maximum is your per-operation limit (USD {{MAX_USD}} by default)
 
{"merchantOrderNo": "CRD...", "status": "PENDING", "cardNo": "WB...", "data": {...}}
  • The total (load + card fee) is held from your float, then charged when the card processor confirms. If the float is too low you receive 402 and nothing is sent.
  • Keep the merchantOrderNo (the operation) and the cardNo (the card).
  • The operation becomes final with an operation.updated webhook, usually within minutes. The card's status changes from pending to active (Normal) and a card.updated webhook is sent.

6. Webhooks

Give Mamlaka an HTTPS endpoint on your backend. Mamlaka sends a POST with a JSON body:

{"id": "...", "type": "operation.updated", "createdAt": "2026-10-30T12:00:00Z",
 "data": {"reference": "CRD...", "type": "CREATE_CARD", "status": "SUCCESS", "customerId": "C10482"}}

Headers: X-Mamlaka-Signature (see below) and X-Mamlaka-Event-Id (the same as id).

Events

Eventdata fieldsYour action
kyc.status_changedcustomerId, holderId, status, approved, reason Update the customer's KYC state; save holderId; notify the customer
operation.updatedcustomerId, reference, type, status An issuance or deposit is final (SUCCESS / FAILED): settle or refund your customer
card.updatedcustomerId, cardNo Refresh the card list and show the new state

type in operation.updated is CREATE_CARD, DEPOSIT, FREEZE or UNFREEZE.

Verify the signature

The X-Mamlaka-Signature header has the form sha256=<hex>: the HMAC-SHA256 of the raw request body, keyed with your webhook secret. Reject any request whose signature does not match. Compute it over the raw bytes, before any JSON parsing.

import hmac, hashlib

def valid(raw_body: bytes, header: str, secret: str) -> bool:
    expected = "sha256=" + hmac.new(secret.encode(), raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(header or "", expected)
// Node.js
const crypto = require("crypto");
function valid(rawBody, header, secret) {
  const expected = "sha256=" + crypto.createHmac("sha256", secret).update(rawBody).digest("hex");
  return header && header.length === expected.length &&
         crypto.timingSafeEqual(Buffer.from(header), Buffer.from(expected));
}

Acknowledging and retries

  • Reply with any 2xx status to acknowledge.
  • Any other response is retried after 1 min, 5 min, 30 min, 2 h, 6 h, then daily.
  • Delivery is at least once: record each event id and ignore repeats.
  • Webhooks say what changed. When in doubt, read the current state from the API.
Tip Acknowledge quickly and do the heavy work (database updates, push notifications) in a background job, so slow processing does not trigger retries.

7. Good practice

  • Save the links between externalId and holderId, and between each action and its Idempotency-Key and merchantOrderNo.
  • Quote, then charge. Call GET /quote before each issuance or deposit and charge your customer from that figure plus your margin.
  • Hold, don't refund, on uncertainty. Debit your customer first; refund only on a definitive refusal or a final FAILED. Keep the money held while an operation is PENDING or UNKNOWN.
  • Retry with the same key. Only ever retry with the same Idempotency-Key; a new key means a new action.
  • Don't rely on webhooks alone. Run a job that polls GET /operations/{reference}?refresh=true for operations still open after a few minutes, and GET .../kyc?refresh=true for customers waiting too long.
  • Watch the float. Alert your finance team before the balance gets too low to issue cards.
  • Validate before submitting. Check name length, date formats, address characters and file sizes in the app to avoid 422s and rejections.
